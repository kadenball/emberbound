# 0.27 — Hold the racket

Combat previously ignored an unexpected stop of its audio context. It could keep running without audible warnings. The sound unlock path also retried `suspended` contexts but skipped `interrupted`. The mixer now reports unexpected suspension/interruption while enabled audio is in use; the game pauses, clears held controls and displays an interruption notice. Restoring the audio device alone keeps combat paused. A deliberate resume gesture retries either state without changing Music/SFX preferences. Fully muted play does not pause over an unused audio device.

The Web Audio specification distinguishes these states and defines interruption recovery. A browser may still reject a resume while an external interruption continues; the game catches that rejection and can retry on another gesture. This is an application-level recovery path, not a workaround proven against every Safari or device audio bug. [Web Audio interruption handling](https://webaudio.github.io/web-audio-api/#handling-an-interruption-on-the-audiocontext), [resume algorithm](https://webaudio.github.io/web-audio-api/#dom-audiocontext-resume).

Two regression tests failed before the fix and pass afterward. One truly suspends a browser audio context, then exposes `interrupted` through a controlled getter to exercise that contract; it verifies that a new gesture resumes the graph while retaining mute and pause choices. That fixture is not a physical iPhone interruption. The other suspends the actual live game's browser audio context, verifies the pause UI and stopped chapter transport, restores the context, and verifies that only an explicit game-resume action restarts combat. It also verifies that disabling both sound and music prevents an unnecessary pause. [Baseline failure states](AUDIO-RECOVERY-BASELINE-0.27.json).

This investigation started with the intermittent WebKit zero-signal observation from 0.24. Before changing product code, six isolated WebKit repetitions passed, followed by a three-platform repeated audio matrix with 21 passes and six inapplicable skips. That initial silence did not reproduce. The new recovery fix addresses a separately demonstrated gap; it does not establish that the original startup issue is resolved. Failed audio tests now attach media state, context state/time and gain information to help distinguish future loading, graph and analyser failures.

After the fix, all 13 applicable focused audio checks pass across desktop Chromium, Android-sized Chromium and iPhone-sized WebKit; two duplicate decoder cases are skipped. All 209 simulation tests pass. The installed **0.27 Android APK** also passes the eight native emulator checks for offline input, audio transport, preferences, Home/Back interruption and saved-profile recovery after process death. The dedicated API 36 emulator has audio output disabled: its transport checks are not evidence of audible speaker/headphone output. Native iOS compilation and physical audio interruptions remain unverified.

The earlier regional scores, cues, cart interaction and Count Snackula changes remain. No combat rules or compositions changed in this pass. Current release verification and the remaining quality gaps are in [validation](VALIDATION.md).

The final complete browser run passed **176 checks**, with ten inapplicable combinations skipped, in one uninterrupted run. This includes the new audio recovery cases and existing campaign ending, co-op, controller, bookmark, cargo, boss and supply flows. No product code changed after that run. The README audio attribution was also corrected to distinguish the selected menu recording from original compositions and synthesized effects.
